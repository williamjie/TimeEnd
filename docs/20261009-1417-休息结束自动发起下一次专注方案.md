## 1. 背景与问题

用户期望：

1. **休息时长到期后**，若已配置「自动发起下一次工作」，则自动开始下一轮专注。
2. 若**未配置**自动发起，则休息结束后停留在待命状态，**由用户手动点「开始」**。

当前实现与期望不一致，属于行为缺口/Bug。

## 2. 代码现状（结合现有实现）

### 2.1 配置项

| 配置 | 位置 | 实际用途 |
|------|------|----------|
| focusDuration | 设置 + electron-store | 专注倒计时，有完整 Timer |
| breakDuration | 设置 + electron-store | **仅展示/保存**，未驱动休息结束 |
| openAtLogin | 设置 | 开机自启 |
| 自动发起下一次工作 | **不存在** | — |

结论：设置里虽有「休息时长」，但没有「休息结束后自动开始下一次专注」开关；breakDuration 也没有被主进程用来结束休息。

### 2.2 休息如何开始

主进程 `src/main/main.js`：

- **专注自然结束**（Timer 的 onComplete）：立刻设 `restStartTime = Date.now()`，发 `rest-started`，再弹强制中断窗。
- **用户点停止**：先弹 stop 模式输入窗；提交/跳过后在 `runStopAftermath` 里设 `restStartTime` 并发 `rest-started`。

两处都只「开始记休息」，**没有**按 breakDuration 启动休息倒计时。

### 2.3 休息如何展示

主窗 `src/renderer/scripts/main.js`、小窗 `mini-renderer.js`：

- 收到 `rest-started` 后本地每秒刷新「本次休息：X 分钟」。
- 这是**已休息时长累加**，不是「还剩几分钟休息」倒计时。
- 没有「休息结束」事件，也不会在到期时改 UI 状态。

### 2.4 休息如何结束 / 下一轮专注如何开始

唯一收尾路径：用户再次点「开始」→ IPC `start-timer`：

1. `saveRestSessionIfAny()` 写休息记录；
2. 清 `restStartTime`，发 `rest-cleared`；
3. 新建专注 Timer 并启动。

因此：

- 休息**不会**因 breakDuration 到期而结束；
- **永远**需要手动「开始」才能进入下一轮；
- 若用户很久不点开始，休息时长会一直涨，直到下次开始才落库。

### 2.5 相关文件

| 文件 | 角色 |
|------|------|
| src/main/main.js | 休息起止、写会话、启动专注 |
| src/main/timer.js | 通用倒计时（可复用做休息 Timer） |
| src/renderer/index.html | 设置 UI（尚无自动发起开关） |

## 3. 目标行为（验收标准）

| 场景 | 期望 |
|------|------|
| 未勾选「自动发起下一次工作」 | 休息倒计时结束后进入「休息结束 / 待命」，**不**自动开专注；用户手动点「开始」 |
| 已勾选「自动发起下一次工作」 | 休息倒计时结束后自动开始下一轮专注，并**弹出提示小窗**，明确告知「该开始工作了」 |
| 休息进行中用户提前点「开始」 | 与现网一致：立刻结束休息、写记录、开专注；取消未到期的休息倒计时 |
| 主窗 / 小窗 | 状态一致；自动发起时两边同步进入「专注中」 |

## 4. 推荐方案（已定稿倾向）

### 4.1 新增配置

字段建议：`autoStartNextFocus: boolean`

- 默认：`false`（安全默认：不突然开计时）
- 设置页：在「休息时长」下方增加勾选，文案建议：
  - **休息结束后自动开始下一次专注**
- 持久化：写入现有 config（get-config / save-config 一并读写）
- 小窗无需单独设置入口（跟主设置走即可）

### 4.2 主进程：休息倒计时生命周期

建议在主进程维护 `restTimer`（复用 Timer，时长 = 当前 breakDuration）：

```text
专注结束 / 停止收尾（中断窗完成后）
  → 置 restStartTime，广播 rest-started
  → 启动 restTimer(breakDuration)
       ├─ onTick：可选广播 rest-remaining（给 UI 倒计时）
       └─ onComplete：onRestFinished()
```

`onRestFinished()`：

1. 停止 `restTimer`；
2. 若尚未写入本次休息：按 `restStartTime` → 现在写一条休息记录（与 `saveRestSessionIfAny` 对齐，避免重复写）；
3. 清休息计时状态，广播「休息结束」（建议新 IPC：`rest-finished`）；
4. 读配置：
   - `autoStartNextFocus === true` → 内部启动下一轮专注，并弹出「开始工作」提示小窗；
   - 否则 → 保持待命，等用户手动 `start-timer`。

用户提前点「开始」时：先 `restTimer.stop()`，再走现有 `start-timer`（内部已有 `saveRestSessionIfAny`）。

### 4.3 与强制中断窗的时序（已定）

现状差异：

- **自然结束**：先设 `restStartTime`，再弹中断窗 → 休息计时与填表重叠。
- **停止**：中断窗关闭后才在 `runStopAftermath` 里开始休息。

**已定约定：**

- 休息倒计时从「中断窗提交/关闭完成」后再正式开始（自然结束与停止路径对齐）。
- 「本次休息」展示也从这个时刻起算，避免填表时间计入休息，也避免与中断窗打架。
- `onRestFinished` / 自动开始前必须断言：`interruptWindow` 为空、当前无运行中的专注 timer。

### 4.4 UI 展示建议

休息中 / 休息结束（未自动开始）：

- 保留「本次休息：X 分钟」累加；
- 休息进行中增加「休息剩余：mm:ss」（主窗 + 小窗）；
- 收到 `rest-finished` 且未自动开始：状态文案改为「休息结束，可开始下一次专注」；
- 未自动开始时：**不额外弹窗**，只改文字即可。

自动开始时（已定，需明显提示）：

- **不要静默开始**。
- 自动启动下一轮专注后，再弹出一个**小型置顶提示窗**，文案要足够醒目，例如：
  - 标题：休息结束
  - 正文：该开始工作了，下一轮专注已自动开始。
  - 按钮：知道了（关闭提示窗）
- 提示窗要求：
  - 置顶（alwaysOnTop）
  - 尺寸小、内容短、一眼能看懂
  - 不阻挡「已开始计时」；用户关掉提示窗后计时继续
  - 若已有同类型提示窗，不重复叠多个
- 主窗 / 小窗状态同步切到「专注中」；提示窗只负责「提醒你该干活了」，不承担开始/停止控制。

### 4.5 「开始工作」提示小窗（新增）

建议实现方式：

| 项 | 建议 |
|----|------|
| 实现位置 | 主进程新建轻量 BrowserWindow（类似 interrupt，但更小、非强制输入） |
| 触发时机 | 仅当 `autoStartNextFocus=true` 且休息倒计时正常结束并已成功启动下一轮专注后 |
| 关闭方式 | 点「知道了」或点窗体关闭；关闭后不影响正在进行的专注 |
| 与强制中断窗区别 | 强制中断窗用于「上轮结束记事」；本窗仅用于「下轮已自动开始」的醒目提醒 |
| 不触发场景 | 用户手动点「开始」提前进入下一轮时，不弹此窗 |

### 4.6 休息记录落库时机

建议统一为：

| 事件 | 行为 |
|------|------|
| 休息倒计时正常结束 | 立即写休息记录（时长按实际休息区间） |
| 用户提前开始 | 仍在 start-timer 里写（若未写过） |
| 防重 | saveRestSessionIfAny 写完后清 restStartTime，避免双写 |

## 5. 方案对比（简要）

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A. 主进程 restTimer + 配置开关（推荐） | 到期逻辑集中在 main | 主/小窗一致、可靠 | 需处理中断窗时序 |
| B. 渲染进程本地 setTimeout 到期再 IPC | 前端判断是否自动开始 | 改动面看似小 | 双窗易不同步、窗口隐藏时不可靠 |
| C. 仅加开关、仍不真正结束休息 | 到期只 auto-start | 实现快 | 「休息结束」语义仍糊，未修根因 |

**推荐 A。**

## 6. 改动清单（实现时）

## 7. 已确认决策

1. **自动发起默认关闭**：`autoStartNextFocus=false`
2. **自然结束后休息起点**：从中断窗提交/关闭完成后再开始算休息倒计时
3. **未自动开始时**：休息结束只改状态文案，不额外弹窗
4. **自动开始时**：不再静默；**弹出小型置顶提示窗**，明确告诉用户「该开始工作了」，下一轮专注已自动开始
